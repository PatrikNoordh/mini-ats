# Data safety map

How Mini-ATS keeps data from being lost, left half done, or seen or changed by another customer. It lists where each piece of data lives, what a delete takes with it, who may read and write what, which guard stops each mistake, and the test that proves the guard works.

`/ats-data-safety` keeps this map up to date (ATS-60). In diff mode, run by `/ats-review-pr`, it reads this map and only the chains a branch touches. In full mode, run by `/ats-epic-close`, it rebuilds the map from the schema, the policies, the Edge Functions and the scripts.

**Last full run:** 2026-11-08, on `main` at `76607a0` (after PR #115, ATS-57). Built from the 21 migrations applied to a fresh Postgres 17 database, with `supabase/tests/rls_test.sql` passing (checks 1–50).

**Rules for this file.** The repo is public, so this file holds no secrets, no real data and no open vulnerability. A gap is written down only once it has an issue or a line in `TICKETS.md`, and a gap that a customer could use against another customer goes to an issue with the `security` label first. Once there are real customers, such a gap goes to a private GitHub security advisory instead, and this file says only that one is open.

## 1. Where the data lives and what a delete takes with it

Every customer row carries `customer_id`, which since ATS-44 is a company id: a row of `companies`, which `company_members` links to its users, one company per user. Each company migrated in ATS-44 kept its first user's id, so for those the same id still names the Auth user, the profile, the company, the owner of every row and the folder in the `cvs` bucket, until the login swap (ATS-58) gives the first users new ids (`docs/next-teams.md`). A company created later, by the seeds since ATS-45 among others, has an id of its own. The app reads a customer user's data by their company's id, from their membership, never by their own id (ATS-45).

| Data                            | Owner key                                                                        | References (on delete)                                                                                                                               | Deleting it also removes                                                                                                                         |
| ------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auth.users`                    | `id`                                                                             | —                                                                                                                                                    | its `profiles` row (cascade), and through it its membership. Never company data, and not its CV files: Storage has no foreign key                |
| `profiles`                      | `id` = the Auth user's id                                                        | `auth.users(id)` cascade                                                                                                                             | its `company_members` row (cascade), nothing else: no customer table references `profiles` (check 51)                                            |
| `companies`                     | `id`                                                                             | none: no foreign key to `profiles` or `auth.users`, even where the ids match (check 51)                                                              | its `company_members`, `jobs`, `candidates`, `applications`, `cv_assessments` and `pipeline_stages` (cascade on `customer_id`). Not its CV files |
| `company_members`               | `(company_id, user_id)`, `user_id` unique                                        | `companies(id)` cascade · `profiles(id)` cascade                                                                                                     | nothing                                                                                                                                          |
| `jobs`                          | `customer_id`                                                                    | `companies(id)` cascade                                                                                                                              | nothing: a job with cards cannot be deleted (`applications.job_id`, no action)                                                                   |
| `candidates`                    | `customer_id`                                                                    | `companies(id)` cascade                                                                                                                              | their `applications` (cascade), and through them their `cv_assessments`. Not the CV file                                                         |
| `applications` (cards)          | `customer_id`, set from the job                                                  | `candidates(id)` cascade · `jobs(id)` no action · `(stage_id, customer_id)` → `pipeline_stages(id, customer_id)` no action · `companies(id)` cascade | their `cv_assessments` (cascade)                                                                                                                 |
| `cv_assessments`                | `customer_id`, set from the card                                                 | `applications(id)` cascade · `companies(id)` cascade                                                                                                 | nothing                                                                                                                                          |
| `pipeline_stages` (columns)     | `customer_id`                                                                    | `companies(id)` cascade                                                                                                                              | nothing: a column with cards cannot be deleted (the composite key, no action)                                                                    |
| `storage.objects`, bucket `cvs` | the first folder of the path, `<customer_id>/<candidate_id>.pdf`, the company id | none to the tables                                                                                                                                   | nothing. Private bucket, PDF only, at most 5 MB                                                                                                  |

**Why `no action` and not `restrict`** on the two keys that block a delete (ATS-38): `no action` is checked at the end of the statement, so a company delete, which removes the cards and the columns in the same statement, still goes through in any order. A single job or column with cards is still refused (`23503`).

**Rows kept in step by triggers, not by the client** (security rule 7):

- `applications.customer_id` comes from the job, and the job and the candidate must have the same customer (`job_candidate_customer_mismatch`).
- `cv_assessments.customer_id` comes from the card (`application_not_found` without one).
- A new card without a column lands in the customer's first open column (`applications_2_start_stage`, which runs after `applications_1_set_customer` because of the names, check 54). `customer_id`'s placeholder default is the nil UUID, as `stage_id`'s.
- Clearing `cv_path` removes the candidate's assessments (`candidates_remove_assessments_with_cv`), since they were made from that file.
- `candidates.cv_uploaded_at` is stamped by the database, never by a client.
- Every new company gets the six default columns (`companies_default_stages`); a new user gets none (checks 35, 56).
- A job's or a candidate's `customer_id` never changes once written, not even for an admin or the service role (`jobs_keep_customer`, `candidates_keep_customer`, `owner_change_not_allowed`, check 55).
- Until a later ticket drops `profiles.company_name`, a company's first user's profile renames the company when the ids match (`profiles_sync_company`). Deleting or restoring a user never deletes or restores a company (ATS-46, check 56). An account promoted to admin leaves its company, and a membership for an admin is refused (`admin_cannot_be_member`, check 53).

### The delete chains

| What is deleted      | How                                                                                                 | Order, and what a failure leaves                                                                                                                                                                                                                                  |
| -------------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A card (job link)    | client delete on `applications`                                                                     | one statement: the card and its assessment go together                                                                                                                                                                                                            |
| An assessment        | client delete on `cv_assessments` (ATS-56)                                                          | one row; the CV stays                                                                                                                                                                                                                                             |
| A CV                 | `removeCandidateCv` in `src/lib/candidate-cv.ts`                                                    | file first, then `cv_path`. A failure in between leaves a path to a missing file, which the next try clears; never a file nobody can see                                                                                                                          |
| A candidate          | the `delete-candidate` Edge Function, with the caller's JWT only (ATS-56)                           | see § 4                                                                                                                                                                                                                                                           |
| A job                | client delete on `jobs`                                                                             | only without cards (`23503` otherwise)                                                                                                                                                                                                                            |
| A column             | client delete on `pipeline_stages`                                                                  | only without cards, and never the last open, the only Hired or the last Rejected column                                                                                                                                                                           |
| An account, soft     | `admin-manage-account`, `soft_delete_or_demote_account`                                             | `deleted_at` is set under the last-admin lock, then the login is banned; if the ban fails, the mark is undone. The company and its data stay, and its other members keep working (ATS-46). A restore lifts the ban unless the user's company is deleted           |
| An account, for good | `admin-manage-account` "delete for good", or `purge-deleted-accounts` after 30 days                 | one statement: the Auth user, its profile and its membership. Never company data or CV files (§ 4)                                                                                                                                                                |
| A company, soft      | `admin-manage-company` (ATS-46)                                                                     | `deleted_at` is set first, so every member sees nothing at once (`current_company_id()`), then each member's login is banned; if a ban fails, the bans and the mark are undone. A restore lifts the bans of the members not deleted on their own, then unmarks it |
| A company, for good  | `admin-manage-company` "delete for good", or `purge-deleted-accounts` 30 days after the soft delete | the CV folder, then each member's login, then the company, whose rows cascade (§ 4, `_shared/company-purge.ts`)                                                                                                                                                   |

## 2. Who may read and write

### Rows (RLS) and table privileges

Every table in `public` has RLS on. Every customer policy has the same shape: a member of the row's company while the member and the company are active, or an admin.

```
customer_id = (select current_company_id()) or (select is_admin())
```

`current_company_id()` reads the caller's membership, profile and company, and is null for a deleted member, every member of a deleted company and a user without a company. `is_admin()` and `account_is_active()` read `profiles` (security rule 4: `profiles.role`, never `user_metadata`). A deleted admin is not an admin. Every customer and storage check signs in as a company's second member, whose id is not the company's, so a policy that still compared with `auth.uid()` would fail (checks 2–7d, 26, 31, 52).

| Table                      | Policies                                                                                 | `authenticated` may            | Column grants (insert / update)                                                                                |
| -------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `profiles`                 | select own or admin; update admin                                                        | select                         | none. Profile changes go through `admin-manage-account`, so the update policy has no grant behind it           |
| `companies`                | select own company or admin                                                              | select                         | none: admins write through the admin Edge Functions (ATS-46), never a client (check 53)                        |
| `company_members`          | select own company's members or admin                                                    | select                         | none: no client joins, leaves or switches a company (check 53)                                                 |
| `jobs`                     | all, owner or admin                                                                      | select, insert, update, delete | all columns. `customer_id` is refused once written (check 55)                                                  |
| `candidates`               | all, owner or admin                                                                      | select, insert, update, delete | all columns. `cv_uploaded_at` is overwritten by the triggers; `customer_id` is refused once written (check 55) |
| `applications`             | all, owner or admin                                                                      | select, insert, update, delete | all columns. `customer_id` is overwritten by the trigger                                                       |
| `cv_assessments`           | select and delete, owner or admin                                                        | select, delete                 | none: only `assess-cv` inserts (security rule 8)                                                               |
| `pipeline_stages`          | all, owner or admin                                                                      | select, delete                 | insert `customer_id, name, position, kind, colour`; update `name, position, kind, colour`. Never `default_key` |
| `storage.objects` in `cvs` | select, insert, update, delete when the first folder is `current_company_id()`, or admin | Storage API                    | —                                                                                                              |

`anon` has no privilege on any table in `public`, also on tables added later (check 20).

`add_stage`, `move_application` and `reorder_stages` are security invoker: RLS decides, as for any write.

### Edge Functions and the service role

Security rule 2: each function verifies the caller first and reads with the caller's JWT. The service role does only the one privileged action the function exists for.

| Function                 | Caller                                            | Service role used for                                                                                                                                                           |
| ------------------------ | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `admin-create-user`      | an admin, checked from `profiles`                 | creating the Auth user (public sign-up is off, rule 3), a customer's new company and their membership; undone if a later step fails (ATS-46)                                    |
| `admin-manage-account`   | an admin, checked from `profiles`                 | updating a profile and its Auth user, moving a user between companies (ATS-46), the soft delete and restore with the ban, and "delete for good" of the login only (ATS-44)      |
| `admin-manage-company`   | an admin, checked from `profiles`                 | creating and renaming a company, the soft delete and restore with its members' bans, and "delete for good" (ATS-46)                                                             |
| `assess-cv`              | the card's owner or an admin, read with their JWT | inserting the assessment                                                                                                                                                        |
| `delete-candidate`       | the candidate's owner or an admin                 | nothing: the JWT only                                                                                                                                                           |
| `purge-deleted-accounts` | pg_cron, with a secret compared in constant time  | everything: the companies due, each with its CV folder, its members' logins and its data, then the accounts due, each with its login only (ATS-46). The one exception to rule 2 |

Outside the Edge Functions, the service role key appears only in `scripts/swap-logins.ts` (the login swap, ATS-58) and `scripts/seed-demo.ts`, which creates each customer's company first, with a new id of its own, and the account as its first member (ATS-45), (from the shell or `.env.seed.local`, with `--yes` required). The end-to-end seed and fixtures use the local stack's fixed key and refuse any host but `127.0.0.1` and `localhost` (`scripts/local-stack.ts`). Never in `src/` (rule 1).

## 4. Database and Storage without a shared transaction

Storage and Postgres cannot commit together, so each flow picks the order whose failure is easiest to recover from. The rule: never leave a file that no row points at, because nobody can see or delete it.

| Flow                                                          | Order                                                                                                         | Worst case, and the way back                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Delete a candidate (`delete-candidate`, ATS-56)               | 1. remove the CV file. 2. delete the row (cascades the cards and assessments). 3. if 2 fails, clear `cv_path` | 1 fails: nothing changed. 2 fails: the candidate stays without a CV and can be deleted again. 2 and 3 both fail: the candidate keeps a `cv_path` to a removed file, so opening the CV fails until it is replaced or the candidate is deleted again. Accepted (epic 8 review, ATS-57 AC6)      |
| Upload or replace a CV (`uploadCandidateCv`)                  | 1. upload to the fixed path. 2. set `cv_path`                                                                 | 2 fails because the candidate is gone: the file just uploaded is removed again. 2 fails otherwise: the old path still names the same file, now with new content                                                                                                                               |
| Add a candidate with a CV (`save-candidate.ts`)               | 1. insert the candidate. 2. upload                                                                            | 2 fails: the candidate is saved without a CV, and the dialog says so (`cv_upload_failed`) and closes, so saving again does not make a duplicate                                                                                                                                               |
| Remove a CV (`removeCandidateCv`)                             | 1. remove the file. 2. clear `cv_path` (removes the assessments)                                              | 2 fails: a path to a missing file, cleared by the next try                                                                                                                                                                                                                                    |
| Delete an account for good (`admin-manage-account`)           | delete the Auth user only; the CV folder and the data are the company's                                       | no Storage step since ATS-44                                                                                                                                                                                                                                                                  |
| Delete a company for good (`admin-manage-company`, the purge) | 1. remove the CV folder. 2. delete each member's login. 3. delete the company, whose rows cascade             | 1 fails: nothing changed. 2 fails: the files of a company already deleted are gone and its `cv_path` values point at nothing; the company, its data and the rest of its logins stay, and the next run finishes. 3 fails: the same, without logins. Nothing is ever left that no row points at |
| Nightly purge (`purge-deleted-accounts`)                      | the companies due, as above, then the accounts due: delete the Auth user                                      | one company or account failing never stops the others; it stays and the next night tries again                                                                                                                                                                                                |
| Assess a CV (`assess-cv`)                                     | reads the CV, then checks that `cv_path` is unchanged before saving                                           | a CV replaced meanwhile gives `cv_changed`, and no assessment of the old file is saved                                                                                                                                                                                                        |

## 5. Decisions to keep

Choices made in earlier tickets that a later change could undo by accident. The skill checks a diff against each one it touches.

- **The candidate delete order (ATS-56).** File first, then the row, then clear `cv_path` if the row stays (§ 4). Clients may read and delete their own assessments; only `assess-cv` creates them (rule 8).
- **`reset_stages` is security definer (ATS-40)**, because a removed default column comes back with its `default_key`, and the column grants keep `default_key` from every client. It checks the caller with the table policy's rule itself, keeps the default columns' ids so their cards stay, and refuses with `23503`, changing nothing, while a column it would remove has cards (checks 48, 49).
- **A new card goes to the first open column, and every customer keeps one (ATS-40 AC7).** The trigger picks the first `open` column by position, whatever it is called; `stage_open_required` refuses removing the last open column or changing its kind (checks 45, 46).
- **The nil UUID default for `stage_id` (ATS-42).** `stage_id` is `not null` with the default `00000000-0000-0000-0000-000000000000`, which no column can have, so the generated Insert type keeps it optional and `applications_start_stage` replaces it. A column the client names must be one of the card's own customer's (the composite key, `23503`).
- **The CLI pin and the deny rules (ATS-57).** The Supabase CLI is an exact dev dependency, `2.122.0`, the same version as CI; both are bumped in one PR (ATS-59, #114). `.claude/settings.json` denies Claude Code every remote Supabase command and reading `~/.supabase/`; the developer runs remote commands.
- **The login swap safety (`docs/next-teams.md`, ATS-58).** `scripts/swap-logins.ts` writes the membership before it deletes anything, so it fails before a delete without the company tables. Before it changes anything it asks `login_swap_blockers()` for a foreign key from a customer table or `companies` to a user, and refuses with `swap_blocked` if there is one (checks 51, 58). It defaults to a dry run, needs `--dump <file>` outside the repo with `--yes`, swaps each company on its own, puts the old email back if the new login cannot be made, and finishes a half-done swap on a new run (`src/test/login-swap.test.ts`). It is tested on the local stack with an old login that owns its CV file (`e2e/login-swap.spec.ts`), and the shares and isolation after a swap in check 59.
- **One id, five meanings, until the login swap (ATS-58).** A migrated company kept its first user's id, so the Auth user, the profile, the company, the row owner and the CV folder share one id. No user's delete may remove a folder or touch the company: only `_shared/company-purge.ts` removes a folder, by company, and `profiles_sync_company` no longer deletes or restores a company (ATS-46, checks 28, 56).
- **`profiles.company_name` stays until a later ticket drops it (ATS-44).** The app reads the name from `companies.name` (ATS-45) and renames a company on the company (ATS-46). `admin-create-user` still fills the column with the company's name, and a trigger still renames a company from its first user's profile when the ids match, for a caller that writes the column. Dropping the column drops that trigger with it.
- **Clients only read `companies` and `company_members` (ATS-44).** Admins add, move and remove users and name, delete and restore companies through the admin Edge Functions (ATS-46), so a client grant on either table is a regression (checks 22, 53).

## 6. The human steps and their order

Some steps reach the project and cannot be checked by CI. They are run by the developer, in this order.

1. **Before the merge, the migration reaches the project.** The developer runs `npx supabase db push --dry-run`, which must list only the branch's migrations, then `npx supabase db push` after a yes. A migration must be backwards compatible with the code on `main`, which runs against it until the merge.
2. **The types are regenerated from the project** and compared by Claude; a diff is committed to the branch.
3. **`rls_test.sql` is run in the SQL Editor** against the project when the migration changes tables, policies or functions, and the PR says it passed.
4. **Edge Functions are deployed** before the merge when the code on `main` calls the new version, and after it otherwise. When a migration and a function change together, the order is decided in the PR (for ATS-44, functions first).
5. **A PR whose migration is applied but is closed without merging** gets a new migration that reverts it.
6. **Who runs what.** Claude never runs a command against the linked project, not even a read-only one; it prints the command, and `.claude/settings.json` refuses the remote ones. For the local stack, Claude runs only `start`, `stop` and `status`. The demo seed and the login swap write to a project only with `--yes`, and Claude never runs either.
8. **The login swap (ATS-58)** runs once, after the code that reads by company is live: a data dump outside the repo first, then the dry run, then `--yes --dump <file>`. Its migration (`login_swap_blockers()`) reaches the project before the merge like any other.
7. **The CLI version** is the one in `package.json`, `2.122.0`, the same as CI.
